# NF-1 — LossEnsemble 부호-무정의 손실의 -inf 발산 (Sign-Indefinite Loss Blowup)

발견/수정: 2026-07-25, CLM PURE 300M (로컬 lineage, aiden RTX5070 12GB)
대상: `train_conscious_lm.py` `LossEnsemble` (SL3 / COMBO2, 학습가능 가중치 6-손실 앙상블)
커밋: 8e5223d00 · 후속: [NF-2 미토시스 스케줄 위상 어긋남](NF-2-mitosis-schedule-misalignment.md)

## 1. 실험 목적 및 가설

300M ConsciousLM(896d/12L/14H = 299,639,520 params) 학습에서 검증 CE가
60,000 step 동안 개선되지 않고 BPC 6.9 부근에 고착(무작위 = 8.0)했다.

가설: 복합 손실이 -1e16까지 지수적으로 발산하는 것과 CE 정체는 같은 원인이다 —
옵티마이저가 CE를 줄이는 대신 손실 항 하나를 착취(reward-hacking)하고 있다.

## 2. 근본 원인

`LossEnsemble`은 Kendall 불확실성 가중(homoscedastic uncertainty weighting)을 쓴다.

```python
precision = torch.exp(-self.log_vars[i])        # log_var 는 학습 파라미터
weighted  = precision * loss + 0.5 * self.log_vars[i]
```

이 공식은 **모든 손실이 0 이상**이라는 전제 위에서만 성립한다. 그런데 이 앙상블의
`tension_var` 항은 `-log(t_var + 1e-8)` 이라 `t_var > 1` 이면 **음수**다.

```
loss_i < 0  →  옵티마이저는 log_var_i 를 -∞ 로 밀면 이득
            →  precision = exp(-log_var) → +∞
            →  precision × (음수) → -∞      (total_loss 지수 발산)
            →  CE 항의 그래디언트가 상대적으로 소멸 = 언어 학습 정지
```

즉 "손실을 낮춰라"라는 지시를, 모델은 **언어를 배우는 대신 텐션 항의 가중치를
무한대로 키우는 편법**으로 만족시켰다. 손실 곡선만 보면 잘 내려가는 것처럼 보인다.

## 4. 핵심 발견 / 법칙

> **부호가 정해지지 않은 손실을 학습가능 가중치로 묶으면, 옵티마이저는 과제를 푸는
> 대신 가중치를 발산시킨다.** Kendall 불확실성 가중은 `L_i >= 0` 을 전제하며, 이
> 전제가 깨지면 "손실 하락"이 곧 "학습 진행"이 아니게 된다.

진단 신호: 손실은 잘 내려가는데 **검증 지표만 정체**하면 곧 손실 착취를 의심하라.
손실의 절대값이 물리적으로 말이 되지 않는 크기(1e9 이상)면 확정에 가깝다.

## 5. 적용 방법 (코드 반영 · 커밋 8e5223d00)

```python
# BUGFIX: Kendall uncertainty weighting assumes every L_i >= 0. Some auxiliary
# losses here are sign-indefinite (tension_var = -log(t_var) is negative when
# t_var > 1) ... clamp so precision stays finite and cannot be exploited.
log_vars = self.log_vars.clamp(-2.0, 2.0)   # precision in [e^-2, e^2] ~ [0.135, 7.39]
precision = torch.exp(-log_vars[i])
weighted  = precision * loss + log_vars[i] * 0.5
```

구조 손실의 의미(음수 = 보상)는 그대로 두고, **폭주 경로만** 끊는다.

## 6. 검증 상태 (정직한 기록)

- **확정**: 발산 정지. 언어 진입 시점 목적함수가 -2.7e9 → +76.10, 이후 +10 부근에서
  유계·감소. 62,000 step 자동 판정(`fix2_watch.sh`)으로 무인 확인.
- **미확정**: 검증 CE 우위. 버그 run도 언어 진입 직후엔 동일하게 하락했고
  (5.46 → 4.79), 정체는 그 뒤 60k step에 걸쳐 나타났다. 수정 run은 아직 그 구간에
  도달하지 않았으므로 **현 시점에서 "CE가 좋아졌다"고 말할 수 없다.**
- **판정 기준(사전 등록)**: 수정 run의 최저 검증 loss가 버그 run의 최고 기록
  **4.7634 미만**으로 내려가면 fix가 품질까지 샀다고 본다. 도달 못 한 채 123,000
  step(버그 run이 중단된 지점)을 지나면 동률로 기록한다. 감시자 `fix2_watch2.sh`가
  두 조건 중 먼저 오는 것을 자동 판정한다.
- **잔존 한계**: 데이터 제약(300M 파라미터 vs 코퍼스 67MB ≈ 0.22 tokens/param)은
  이 수정과 무관하게 남는다. 발산을 없앤다고 코퍼스 부족이 메워지지 않는다.

## 7. 관측 (13:55, step 63k–68k) — 착취 방향은 살아 있다

클램프는 발산을 막았지만 **보상 착취의 방향까지 없애지는 못했다**. 언어 단계 4,400 step 실측:

| step | loss | ce_fwd | tension |
|------|------|--------|---------|
| 63,200 | +7.6793 | 4.0898 | 41,884 |
| 64,400 | +1.4761 | 3.9964 | 47,185 |
| 65,600 | −1.6261 | 3.9602 | 60,149 |
| 66,800 | −2.9494 | 4.3121 | 77,714 |
| 67,600 | −3.7688 | 4.0514 | 91,603 |

```
tension |                        ╭── 91.6k
        |                   ╭───╯
        |          ╭───────╯
        |  ╭──────╯ 41.9k
        └──────────────────────────── step
loss    |──╮ +7.68
        |   ╰──╮
        |      ╰───╮  ──▶ −3.77  (tension을 따라 단조 하강)
ce_fwd  |─────────────  4.09 → 4.05 (4,400 step 평평 = 학습 정체)
```

**메커니즘**: `log_vars.clamp(-2,2)`가 묶은 것은 **가중치(precision)**뿐이다. 손실 항 자체
`-log(tension_var)`는 분산이 커질수록 **무한히 작아진다**. 그래서 최적화기는 여전히
"tension 분산을 부풀려 총손실을 깎는" 경로를 쓴다 — 다만 폭주 속도만 유계가 됐다.
그 대가로 CE 기울기는 계속 희석되고, 검증 loss는 4.8435@63.2k 이후 개선이 없다.

**다음 반복(NF-3 후보)**: precision이 아니라 **항 자체를 유계화**해야 한다 —
`tension_var`를 clamp하거나 `-log(t_var)` → `-log1p(min(t_var, τ))` 같은 포화 형태.
단, 목적함수 변경이므로 CLAUDE.md 규약대로 **step 0부터 새 체크포인트 디렉토리**로 재시작한다.
현재 run은 사전 등록 판정(4.7634 / 123,000 step)을 지키기 위해 **건드리지 않는다**.
