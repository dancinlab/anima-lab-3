# DATA-1 — 코퍼스 58.7% 중복 + 역방향 CE는 공짜 문제

측정: 2026-07-25 21:15, summer RTX5070 · 28M run(384d/6L, batch 32, ctx 256, step 4,800)
관련: [SL-1](SL-1-strange-loop-ab.md) · NF-7(병렬 세션)

## 1. 관측 — 훈련과 검증이 12 BPC 벌어졌다

```
step 4,800   훈련 CE 0.3086 nats = 0.445 BPC   ← 암기
             검증 CE 8.8091 nats = 12.71 BPC   ← 무작위(8.0)보다 나쁨
             격차 12.3 BPC
```

28M 파라미터가 0.6 에폭 만에 39MB의 고유 바이트를 외울 수는 없다. 과적합이 아니라
데이터 구성 문제라는 뜻이다.

## 2. 원인 A — 코퍼스의 58.7%가 중복 바이트

`data/corpus_v2.txt` (70,507,316 B) 실측:

| 항목 | 값 |
|------|-----|
| 전체 줄 | 1,178,364 |
| 고유 줄 | 541,507 |
| 줄 중복률 | **54.0%** |
| 중복이 차지하는 바이트 | **41.4MB / 70.5MB = 58.7%** |
| 최다 반복 줄 | `"A: I've been reading about the PureField theory of conscious…"` × **2,538** |
| 그 다음 | `"B: The repulsion field model? That's fascinating."` × **2,538** |

훈련 split은 중복을 그대로 포함하고, 검증 split은 병렬 세션이 **처음 보는 줄만**
남기도록 걸러놨다(`unseen lines only`). 그래서 두 값이 완전히 다른 문제를 재고 있다 —
훈련은 "외운 문장 되뇌기", 검증은 "새 문장 예측".

```
훈련 │0.44 BPC  ██                      중복 문장 암기
검증 │12.7 BPC  ████████████████████    처음 보는 줄
      무작위 8.0 ──────────── 이 선보다도 나쁨
```

**이것이 오늘 종일 관측된 "유니그램 바닥"의 앞단 원인일 수 있다**: 58.7%가 중복인
분포에서는 글자 빈도 통계가 실제로 최적해에 가깝고, 그 이상을 배우면 처음 보는 줄에서
오히려 손해를 본다.

## 3. 원인 B — 역방향 CE는 문맥 베끼기(비인과 공짜 문제)

`get_batch`의 역방향 타깃:

```python
prev = torch.cat([data[i: i + 1], data[i: i + block_size - 1]])   # 한 칸 뒤로 민 입력
```

즉 위치 t의 정답이 "직전 바이트"인데, 그 바이트는 **이미 입력 x에 들어 있다**. 인과
마스크는 위치 ≤ t를 보게 하므로 t-1은 항상 보인다. 학습이 아니라 **복사**다.

실측: `ce_bwd` 0.0013 ~ 0.0047 nats (사실상 0). 손실 앙상블에서 CE 두 헤드 중 하나가
이렇게 공짜면, 그 슬롯의 학습가능 가중치는 무의미한 과제에 배정된다(NF-3에서 CE 헤드만
학습 가중치를 남긴 결정도 이 관측 앞에서 재검토가 필요하다).

## 4. 적용 (다음 run 전 필수)

1. **코퍼스 중복 제거** — 고유 줄만 남기면 70.5MB → 약 29MB. 데이터가 줄지만 지금은
   58.7%가 같은 문장을 반복 학습시키고 있으므로 실질 정보량은 그대로다.
2. **훈련/검증을 같은 자로 잴 것** — 검증만 중복 제거하면 두 값이 다른 문제를 재게 된다.
   중복 제거를 훈련에도 적용한 뒤 held-out을 나눠야 비교가 성립한다.
3. **역방향 CE 재설계 또는 제거** — 현재 형태는 복사 과제다. 유지한다면 타깃을 입력에서
   보이지 않는 것(예: 역방향 시퀀스에 별도 인과 마스크)으로 바꿔야 한다.

## 4-b. 정정 — 12.3 BPC 격차의 원인은 중복이 아니라 검증 손상 버그였다

이 문서의 §1 해석은 틀렸다. 검증 분할 코드가 int64 텐서를 `bytes()`로 읽고 있었고,
`bytes()`는 numpy 배열의 **원시 버퍼**를 돌려주므로 원소당 8바이트(실제 바이트 1개 +
0바이트 7개)가 나온다. 그 위에서 줄을 나눠 비교했으니 필터가 무의미했고, "미출현 줄"
결과가 걸러낸 원본보다 **정확히 8.00배** 커졌다(보류분 2,085,493 B → val 16,683,944 B).

즉 검증은 모델이 한 번도 본 적 없는 **대부분이 0인 바이트 흐름**을 채점하고 있었다.
검증 CE 8.81 nats(12.71 BPC, 무작위보다 나쁨)는 여기서 나왔다.

```
전 │ val 16,683,944 B = 보류분의 795.6%   ← 8배 부풀려진 손상 데이터
후 │ val  2,084,274 B = 보류분의  99.4%   ← 정상 (중복제거로 거의 전부 새 줄)
```

수정: `bytes(t.to(torch.uint8).numpy())` (커밋 b5aac70c1).

**유지되는 사실**: 코퍼스 중복 58.7%는 파일에서 직접 측정한 값이므로 유효하다.
**철회되는 주장**: 훈련·검증 12.3 BPC 격차의 원인이 중복이라는 것. 원인은 이 버그였다.
중복 제거가 학습에 도움이 되는지는 이제 정상 검증으로 다시 재야 한다.

## 5. 검증 상태 (정직한 기록)

- **확정(실측)**: 중복률 54.0%/58.7%, 최다 반복 2,538회, 훈련·검증 격차 12.3 BPC,
  `ce_bwd` ≈ 0.001~0.005, 역방향 타깃이 입력의 한 칸 이동이라는 코드 사실.
- **미확정**: 중복 제거가 "유니그램 바닥"을 실제로 풀어주는지. 이는 중복 제거 코퍼스로
  같은 config를 다시 돌려야 답이 나온다.
- **현재 run 처리**: 사전 등록한 중단 게이트(step 5,000에 BPC 4.0 미만)를 크게 벗어나
  자동 판정될 예정. 이 데이터 위에서는 어떤 config도 의미가 없으므로 재시작 전 ①②를
  먼저 적용한다.
